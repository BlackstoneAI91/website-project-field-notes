How to hand over an AI feature when its vendor changes

Changing the vendor behind an AI feature is a good time to find out which parts of the product belong to your team. An app may call an external model to suggest a short description for a service request. The app also decides what information to send, who can edit the suggestion and where the final description is saved. A handover should make those boundaries visible so the team can change vendors without quietly changing the service customers receive.

Trace one complete request before listing tools

Pick a routine request and follow it from the screen to the final record. In a fictional property maintenance app, a resident reports a broken light and the system drafts a summary for the service desk. Note where the original report is stored, what the model receives, where its response is checked and which version staff see. Include the screen the resident uses to review the draft if the workflow allows one.

Ask a developer and a service desk colleague to walk through the same request together. The developer may think of the model output as a temporary draft, while the service desk may use it as the first line of every work order. That difference matters when the new provider changes the structure or tone of its response. Write down which fields are contractual, which are internal and which can change without affecting the work. The useful output is a simple map a new teammate can follow.

Separate what you can export from what you must rebuild

Make an inventory of the instructions, examples, settings and business rules needed to reproduce the feature. Start with the prompt templates and any definitions for structured fields. Include shared reference documents only when your team has permission to use them on the new service. Check whether examples are held in your repository, managed through the vendor dashboard or recorded only in an old support ticket. Give each item an owner and an export date.

Some parts may behave differently even when you can copy the text. A response that was limited to one paragraph may need a separate length check with the new service. A vendor-specific workflow may need to become part of your application. Where you depend on a feature you cannot export, describe the outcome it provided and build a small example to demonstrate it. If you work with an AI agency, use that inventory to discuss which differences require new design work and which can be handled through configuration.

Agree which records will move

Decide what data the new service actually needs for the next request. A repair summary may require the description and selected category, with no need for the resident’s name or contact details. Check how the existing application removes fields before a request leaves it. Agree who can inspect example requests, where copies will be kept and when those copies should be removed.

Treat recent service requests and vendor logs as separate from the reusable handover materials. If the team needs realistic examples, start with synthetic ones or examples approved for the specific testing purpose. Keep a note explaining where each sample came from and why it can be used. Test a request that contains unnecessary details and confirm they stay inside the application. You want the second vendor to receive the intended input even if a customer pastes more than the form asks for.

Compare the work a person would actually receive

Create a short comparison set that covers common requests, incomplete requests and unusual phrasing. Show reviewers the original input and the two suggestions side by side without revealing which vendor made which suggestion. Ask whether the wording preserves the issue, whether it adds information the resident did not provide and whether a colleague could act on it. A summary that sounds polished can still be less useful if it removes the detail that distinguishes two faults.

Record outcomes at the level of the task. A reviewer might accept the wording for a broken light and reject a summary that changes the location or implies a repair has been confirmed. For recurring faults, add a test that keeps related requests distinct. Check what happens when the vendor returns an incomplete response. The comparison should show what the product does with the response, including how it flags a draft for review, rather than grading isolated sentences.

Make rollback a task someone can perform

Set a small launch window with an owner and an agreed fallback. Depending on the app, you might limit the new provider to a test group or keep suggestions disabled for a particular queue. Confirm how to stop sending new requests and what happens to work already in progress. Where the old vendor will no longer be available, test the manual workflow that will keep the service running.

Ask the software application development company to demonstrate a rollback using a test request. Check whether the original customer report remains available and whether staff can tell which version produced a draft. A teammate should be able to follow the rollback instructions and confirm the result without needing the person who wrote them. Leave the service desk a short message explaining what they should see during the change and how to raise a problem.

Leave a record the next team can use

At handover, keep the current request map, the export inventory, the comparison results and the rollback steps together. Note which differences the team accepted and which ones need follow-up. Set a date to read a sample of real outcomes after release. If a frequent request has become harder to handle, first check whether the cause is a missing input, an output formatting difference or a change in the way staff review drafts.

A successful change leaves the product easier to understand. The team knows where to update an instruction, where to check a saved result and who can decide to switch the feature off. Use the next vendor review to update the record while the details are still fresh. Published by Blackstone Intelligence Sarawak, Kuching, Malaysia.
